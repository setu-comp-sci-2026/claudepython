# Avoiding Global Variables

Reading a global is fine.  *Modifying* a global from inside a function is a problem — it creates hidden state that makes your program hard to test, understand, and debug.

## The Problem with global

Create a new Python file and enter the bad pattern first:

~~~python
# Bad — hidden global state
total = 0

def add_to_total(value):
    global total        # declares intent to modify the global
    total += value

add_to_total(10)
add_to_total(25)
print(total)    # 35
~~~

Run it — it works.  But the problem is invisible until things go wrong:

- Any function anywhere in the file can change `total` without you knowing
- You cannot test `add_to_total` without first setting up the global
- If two functions both modify `total`, the order of calls matters in subtle ways

## The Better Pattern

Pass data *in* as a parameter and return the result *out*:

~~~python
# Good — no hidden state
def add_values(current_total, value):
    return current_total + value

total = 0
total = add_values(total, 10)
total = add_values(total, 25)
print(total)    # 35
~~~

The function is now *self-contained* — it only depends on its parameters and produces a predictable result.

## Spot the Difference

Run both versions and confirm they produce the same output.  Then consider: which version would be easier to test if you needed to verify that adding `10` and then `25` gives `35`?  With the good pattern you can call `add_values` directly with any inputs. With the bad pattern you would have to reset the global first.
